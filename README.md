# Cinema API — ДЗ 2 (NestJS + PostgreSQL + TypeORM)

REST API кінотеатру: фільми, зали, сеанси та бронювання місць. Це окреме продовження [ДЗ 1](https://github.com/W33nDen/cinema-api-hw1): попередній репозиторій не змінюється. Дані зберігаються в PostgreSQL; масивів-сховищ у сервісах немає.

Головні зміни: схема створюється оборотними міграціями, список сеансів фільтрується й розбивається на сторінки в SQL, а бронювання та всі його місця записуються однією транзакцією. Унікальний індекс БД не дозволяє двічі забронювати те саме місце, зокрема одночасними запитами.

## Швидкий запуск

Потрібні Node.js 22.13+ та Docker із Docker Compose v2.

```bash
# 1. Встановити точні версії залежностей
npm ci

# 2. Створити локальну конфігурацію
cp .env.example .env

# 3. Підняти PostgreSQL (дані зберігаються в Docker volume)
docker compose up -d --wait

# 4. Створити схему виключно міграціями
npm run migration:run

# 5. Додати демонстраційні дані
npm run seed

# 6. Запустити API в режимі розробки
npm run start:dev
```

Після запуску: API — <http://localhost:3000>, Swagger UI — <http://localhost:3000/docs>, OpenAPI JSON — <http://localhost:3000/docs-json>.

Для зупинки бази без втрати даних: `docker compose down`. Команда `docker compose down -v` **видаляє всі дані** й потрібна лише для навмисного початку з порожньої бази.

## Конфігурація

Приклад `.env` (повний зразок також у [`.env.example`](.env.example)):

```dotenv
PORT=3000
NODE_ENV=development
DB_HOST=localhost
DB_PORT=5432
DB_USERNAME=cinema
DB_PASSWORD=cinema_password
DB_DATABASE=cinema
```

| Змінна | Призначення | Обмеження |
| --- | --- | --- |
| `PORT` | Порт API | ціле число 1–65535, типово 3000 |
| `NODE_ENV` | Режим застосунку | `development`, `production`, `test` |
| `DB_HOST` | Адреса PostgreSQL | обов'язковий непорожній рядок |
| `DB_PORT` | Порт PostgreSQL | обов'язкове ціле число 1–65535 |
| `DB_USERNAME` | Користувач БД | обов'язковий непорожній рядок |
| `DB_PASSWORD` | Пароль БД | обов'язковий непорожній рядок |
| `DB_DATABASE` | Назва БД | обов'язковий непорожній рядок |

`ConfigModule` завантажує `.env` і перевіряє клас `EnvironmentVariables` декораторами `class-validator`. Якщо обов'язкового параметра немає або він некоректний, застосунок не запускається. NestJS отримує налаштування через `ConfigService`; CLI використовує ту саму валідацію. Змінні оболонки мають пріоритет над `.env`. Демонстраційний пароль призначений лише для локальної навчальної бази; для інших середовищ задайте власні значення.

`.env`, `node_modules`, `dist` і `coverage` не потрапляють у Git. Файл Compose використовує ті самі `DB_USERNAME`, `DB_PASSWORD`, `DB_DATABASE` та `DB_PORT`. Якщо на вашому комп'ютері порт 5432 зайнятий, змініть `DB_PORT`, наприклад на 5433.

## Міграції та демонстраційні дані

```bash
npm run migration:show     # стан міграцій
npm run migration:run      # застосувати всі ще не виконані міграції
npm run migration:revert   # відкотити останню міграцію
npm run seed              # ідемпотентне засівання
```

`src/database` містить окреме джерело даних для TypeORM CLI та всі міграції. `synchronize` вимкнено. UUID генеруються PostgreSQL через `gen_random_uuid()`, налаштовано `uuidExtension: 'pgcrypto'`.

Кожна міграція має `up` і `down`. Застосовану міграцію не редагують: наступну зміну схеми оформлюють новою. Відкат початкової міграції видаляє її таблиці **разом із даними**; перевіряти відкат слід на окремій тестовій базі.

[`src/seed.ts`](src/seed.ts) додає щонайменше два фільми, два зали, чотири сеанси в різні дати та одне бронювання з місцями. Скрипт запускається після міграцій, використовує стабільні UUID та одну транзакцію: повторний запуск не створює дублікатів і не очищує користувацькі записи.

Для production-запуску:

```bash
npm run build
npm run start:prod
```

Перед запуском production-застосунку міграції потрібно застосувати окремо; сам запуск API схему не створює і не змінює.

Усі попередні форми запитів і відповідей з ДЗ 1 збережено, **крім відповіді списку сеансів**.

### Пагінація, фільтри та сортування сеансів

```http
GET /showings?filmId=<UUID>&date=2030-01-15&page=1&limit=20&sort=asc
```

Усі query-параметри необов'язкові:

| Параметр | Значення | Якщо не передано |
| --- | --- | --- |
| `filmId` | UUID фільму | усі фільми |
| `date` | реальна дата `YYYY-MM-DD`, доба за UTC | усі дати |
| `page` | ціле число від 1 | 1 |
| `limit` | ціле число 1–100 | 20 |
| `sort` | `asc` або `desc` за часом початку | `asc` |

Приклад відповіді:

```json
{
  "items": [
    {
      "id": "00000000-0000-4000-8000-000000000001",
      "filmTitle": "Земля",
      "hallName": "Зал 1",
      "startsAt": "2030-01-15T18:00:00.000Z",
      "price": 12500
    }
  ],
  "total": 1,
  "page": 1,
  "limit": 20
}
```

`total` — кількість усіх записів після фільтрів, а не довжина поточної сторінки. Для порожньої або завеликої сторінки `items` дорівнює `[]`. За однакового часу початку додаткове сортування — `id ASC`, також при `sort=desc`. Фільтри поєднуються через AND. `QueryBuilder` виконує JOIN, WHERE, ORDER BY, OFFSET/LIMIT і підрахунок у PostgreSQL; завантаження всього розкладу з подальшим обрізанням масиву немає.

Неправильна дата, нецілі/поза межами `page` чи `limit`, інше значення `sort` або невідомий query-параметр дають **400**. `startsAt` приймає ISO 8601 у майбутньому; без часового зсуву час вважається UTC. У відповідях час завжди нормалізовано до UTC.

### Правила бронювання та цілісності

Ціни — цілі числа в копійках: 125 грн = `12500`; `totalPrice = price × кількість місць`. Сума має вміщуватися в PostgreSQL `integer`.

Бронювання приймає `{"seats":[{"row":1,"seat":2}]}`. Порожній список, повтор одного місця або місце поза залом дають **400**. Якщо хоча б одне місце зайняте — **409**, і не зберігаються ні бронювання, ні жодне нове місце.

Сервіс записує `bookings` і всі `booking_seats` через transaction-scoped `EntityManager` в одній транзакції `DataSource`. Унікальний індекс `(showing_id, row, seat)` гарантує захист і при конкурентних запитах. Помилка PostgreSQL `23505` перетворюється на зрозумілу **409** без SQL-тексту. Видалення бронювання запускає `ON DELETE CASCADE` для його місць: вони знову доступні.

Зали мають унікальну назву без урахування регістру та пробілів по краях. Фільм/зал із будь-яким сеансом видалити не можна — **409**. Зовнішні ключі не дозволяють каскадно знищити сеанси разом із фільмом чи залом.

### Формат помилок

Глобальний фільтр повертає один формат; `message` — рядок або масив повідомлень валідації:

```json
{
  "statusCode": 400,
  "timestamp": "2026-11-12T11:00:00.000Z",
  "path": "/showings?page=0",
  "message": ["page має бути не менше 1"],
  "error": "Bad Request"
}
```

Неочікувані внутрішні помилки повертають **500** із загальним повідомленням, не розкриваючи деталей БД. Деталі залишаються лише в серверному журналі.

## Перевірка

[`requests.http`](requests.http) містить запит до кожного маршруту та всі описані випадки помилок. Виконуйте зверху вниз у VS Code REST Client: ідентифікатори беруться зі змінних відповідей, вручну підставляти UUID не потрібно. Для залів використано часові мітки в назвах, тому перевірку можна повторювати без очищення бази.

```bash
npm run build
npm run lint
npm test -- --runInBand
```

Для інтеграційних тестів створіть **окрему** порожню базу:

```bash
docker compose exec postgres createdb -U cinema cinema_test
npm run test:e2e
```

Якщо база вже існує, повторювати `createdb` не потрібно. Тести самі застосовують міграції й очищують тільки `cinema_test`. За потреби задайте `TEST_DB_DATABASE=інша_назва_test`; назва обов'язково має закінчуватися на `_test`, інакше очищення заборонено. Параметри підключення беруться з локального `.env`.

E2E-перевірки використовують реальну PostgreSQL: попередні маршрути, валідацію, пагінацію та стабільне сортування, UTC-фільтр, конфлікти FK, відкат бронювання, два паралельні запити на те саме місце, каскадне звільнення місць, збереження даних після перезапуску та Swagger-контракт нової відповіді.

## Структура

```text
src/
├── app.module.ts                 # ConfigModule, DatabaseModule, доменні модулі
├── main.ts                       # ValidationPipe, HttpExceptionFilter, Swagger
├── config/environment-variables.ts
├── database/                     # спільні налаштування, CLI DataSource, міграції
├── seed.ts                       # повторюване засівання без дублікатів
├── common/                       # помилки, UUID/date-утиліти, валідатори
├── films/                        # TypeORM-сутність, репозиторій, DTO, контролер
├── halls/                        # TypeORM-сутність; місця обчислюються з розміру залу
├── showings/                     # сутність, QueryBuilder, пагінована відповідь
└── bookings/                     # Booking + BookingSeat, транзакції та схема місць
```

TypeORM-сутності розміщені в `entities` своїх доменних модулів; вони відокремлені від Swagger-моделей відповіді. Модулі підключають репозиторії через `TypeOrmModule.forFeature`, сервіси містять бізнес-правила, а контролери — маршрути та документацію. Схема має п'ять таблиць; `booking_seats` зберігає кожне зайняте місце окремим рядком. Циклічних залежностей і `forwardRef` немає.
